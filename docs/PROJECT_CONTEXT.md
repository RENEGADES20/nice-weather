# 产品范围与工作边界

更新：2026-10-10。当前事实见 [CURRENT_STATE](CURRENT_STATE.md)，交付顺序见 [PROJECT_REBASELINE](PROJECT_REBASELINE.md)。

## 产品目标

建设可日常运行的个人桌面天气交易终端，覆盖市场选择、天气分析、策略解释、人工订单、自动策略、账户与持仓、风险、回测及复盘。完整功能交付为目标，早期 MVP 范围不再限制本阶段。

首阶段固定 KNYC、Kalshi 与 Polymarket US。第二阶段用一座实际城市检验复用能力，城市待选。Poly Intl 不参与当前开发、部署或验收；KLGA 原数据及研究独立保留，不能改标签冒充 KNYC。

## 用户实际工作流程

1. 选择平台、城市、市场日及档位，查看规则、天气、价格和数据时间。
2. 查看每个策略为何等待、触发或拒绝；选择模拟/实盘账户并设置风险。
3. 下单、撤单、查看成交及持仓；停止策略；刷新或重连后继续操作。
4. 选择历史天气或交易回测，检查覆盖、参数和成交假设，运行并解释结果。
5. 从图表事件追溯策略输入、订单和账目；对账结算。

交易、天气/策略、回测、账户/运行诊断采用清楚的工作区。交易入口只加载当前任务需要的数据；工程版本、路径、采集明细和大型历史列表放入按需展开的诊断。具体界面增删由真实操作与性能测量决定。

## 研究与交易事实

历史天气可用于触发频率、条件命中、升温结束概率和结算温度误差研究。价格相关策略还需要历史价格；收益、手续费、流动性及成交率必须说明数据与模拟假设。最终 CLI 作为结果标签，不能提前变成当天可知输入。缺真实 received_at 时保留 source-time 研究标签和延迟假设。

优先级：已有本地/R2/研究资产 → 官方历史下载 → 可核验的第三方数据。仅当一个明确策略需要且外部历史缺失时，另提最小新增采集方案，列明范围、容量及费用；不默认搭建长期行情采集平台。

## 交易和数据边界

- Live 默认关闭。用户已表达允许 agent 提交真实订单，金额与账户范围后补；参数不齐不启用，实际执行服从工具与平台边界，必要的人工提交由用户完成。
- 不充提或转移资金；密钥仅服务端读取，不进入仓库、日志、前端或研究包。
- 合约站点、当地日、温标、档位、舍入、观察窗口、结算源与版本必须明确；歧义进入可解释的 no-trade。
- Paper/Live 隔离；未知订单先对账，不因超时重复发单。回滚不得以旧库覆盖新成交。
- 批量删除文件必须列出精确目标并取得人工确认。
