# 项目长期 Context

最后更新：2026-09-19

## 1. 项目目标

本项目建设个人桌面天气市场交易终端，统一实时市场、天气、策略信号、人工/自动交易、订单、持仓、收益和回测。

当前交付：KNYC（Central Park），Kalshi 优先、Poly US 其次；Poly Intl 暂不开发、部署或验收。原 KLGA 的 S1/S2/S3 全部迁移，保留历史数据与研究对照。Nautilus 模拟/回测已接入，继续复用订单与账户事件。

允许实盘接口开发与部署，用户配置账户、市场白名单、风险额度并主动启用；Agent 不执行真实资金验收。当前没有充分验证的稳定盈利策略。完成事实和缺口见 CURRENT_STATE.md；验收清单见 KNYC_TERMINAL_DELIVERY.md。

## 2. 系统主链

```text
研究证据
→ 市场与天气数据采集
→ 带版本的事件存储
→ 合约映射
→ Tmax 概率分布
→ 策略候选
→ 风险审批与 no-trade
→ 订单和库存执行
→ 历史回测 / 实时纸盘
→ 监控、对账和复盘
```

每一层都有独立职责。一个准确的天气判断仍可能因站点映射、数据时间、价格、滑点、旧订单或库存问题产生亏损。

## 3. 核心设计原则

### 当时信息原则

任何历史判断只能使用该时刻之前已经收到的数据。天气页面后续修订、补录观测和最终报告不能提前进入历史回放。

关键数据需要保存：

- 来源时间 `source_time`。
- 本地接收时间 `received_at`。
- 数据版本。
- 修订或删除记录。
- 当时有效的合约规则版本。

### 合约真相优先

每份合约必须明确：

- 气象站。
- 当地日期与时区。
- 摄氏或华氏。
- 温度档边界。
- 舍入或截断规则。
- 观测窗口。
- 最终结算来源。
- 结算触发条件。

无法消除歧义时，系统输出 `no-trade`。

### 概率分布优先

系统预测站点最终日最高温 `Tmax` 的完整分布，并按合约规则映射为整组温度档概率。单个点预测无法充分表达档位边界和尾部风险。

### 可执行价格优先

策略使用真实 Bid、Ask 和订单簿深度。候选优势需要覆盖费用、滑点、模型误差、部分成交和退出成本。

### 纸盘优先

实盘接口可持续开发；启用前必须验证数据、回放、订单状态、重连、撤单、库存、结算与对账，模拟和真实资金验收分开记录。

## 4. 当前研究假设

现有作者研究与逆向工程形成以下方向：

- 特定机场和天气型下的模型条件偏差。
- 当前实况已经偏离旧模型路径，而市场尚未完成调整。
- 临近日最高温时，用 METAR、温度斜率、云雨、风和附近站点更新剩余升温空间。
- 两个相邻温度档的联合概率与联合成本出现差异。
- 天气或结算数据修订后，盘口可能保留旧报价。
- 整组互斥温度档存在联合价格矛盾。
- 数据稳定期选择性提供流动性，信息更新前减少报价或撤单。

这些方向均为待检验假设。作者收益截图、倍数和自信表达不进入收益率先验。

## 5. 技术方向

Nautilus Trader 是已接入的交易运行引擎，负责事件流、订单、持仓、重连、对账以及回测和 Sandbox 接口。

本项目自己掌握：

- 天气与结算数据。
- 合约映射。
- Tmax 概率模型。
- 策略研究。
- 领域风险与 `no-trade`。

业务模块通过清晰接口连接运行引擎，以便未来替换技术底座。

## 6. 研究工作流

天气作者研究采用：

```text
原帖或案例
→ 原子主张
→ 可测量机制
→ 可证伪假设
→ 策略规格
→ 历史检验
→ 实时纸盘
```

作者原话、项目推断和未验证假设必须分开保存。反例、亏损和异常具有较高研究价值。
